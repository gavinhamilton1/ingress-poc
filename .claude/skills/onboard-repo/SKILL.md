# Repo onboarding agent

Turns "here's a git repo" into a reviewed, checked-in Route CRD plus a live
request-payload validator at the gateway — without the developer hand-writing
either.

## What this produces

1. **A Route CRD YAML** — one per discovered HTTP endpoint, in the exact
   schema `k8s/crds/route.ingress.jpmc.com.yaml` defines.
2. **An OPA Rego policy** per endpoint that accepts a request body — checks
   required fields and per-field format (email/phone/date-of-birth-shaped
   fields get real format regexes; everything else at least gets type and
   presence checks). It does **not** duplicate generic SQLi/XSS/NoSQL-
   injection checks — see "Two tiers of policy" below for why.

Nothing is registered against the live platform until the developer
explicitly approves both artifacts. This is the "review and check in" gate —
treat it as a hard stop, not a formality.

## Two tiers of policy — know this before writing Step 3's Rego

There's a **global policy** (package `ingress.policy.payload.global`,
managed via the `get_global_policy`/`update_global_policy` MCP tools, not
by this skill) that `auth-service` evaluates against **every** route with a
request body — including routes that have never been through this skill at
all. It carries only the generic injection-pattern checks (SQLi/XSS/NoSQL
markers). It runs first; only if it allows does the route-specific policy
this skill generates get evaluated.

This split exists so a newly discovered attack pattern can be blocked
platform-wide with one policy update, instead of regenerating and
reattaching every individual route's policy. It also means: **do not
generate injection-pattern checks in the route-specific policy** — that
would just duplicate what the global policy already covers. Route-specific
policies generated by this skill should only ever check things unique to
that route's own schema (required fields, formats) — see Step 3.

## Prerequisites

- The `cib-ingress` MCP server must be configured and reachable (see
  `MCP.md` at the repo root) — this skill calls its `create_route` and
  `attach_payload_policy` tools, backed by `management-api` on
  `http://localhost:8003` (or in-cluster).
- `management-api` and `auth-service` should be running (`docker compose up`
  or the kind cluster) for the generated policy to actually take effect —
  the YAML/Rego generation and review steps work without them, but
  activation calls `management-api` directly. Payload policies (both the
  global one and route-specific ones from this skill) are compiled and
  evaluated in-process by `auth-service` via the OPA Go SDK — no separate
  OPA network call in this path, so the standalone `opa` container isn't
  a dependency for this feature (it's still used for an unrelated
  role-based check elsewhere in the platform).

## Inputs

Ask the user (if not already given) for:

- **`repo`** — a git URL or local path to clone/scan.
- **The target fleet.** Routes in this platform live under Fleets, and
  Fleets are grouped by LOB in the console — a route registered with no
  fleet is an orphan that won't show up grouped anywhere sensible, and (see
  "Resolving the fleet" below) `create_route` has no real fleet-association
  mechanism at all, just a hostname that happens to string-match a fleet's
  subdomain. Resolve this properly, don't skip it:
  1. Ask **which LOB** this service belongs to. Values actually in use
     today: `Markets`, `Payments`, `Global Banking`, `Security Services`,
     `xCIB` — it's a free-form string, not an enforced enum, so an
     unfamiliar answer isn't a blocker.
  2. Call `list_fleets`, filter to that LOB, and show the developer what
     already exists (name + subdomain). Ask: **use one of these, or create
     a new fleet?**
- **`backend_url`** — where the service is actually reachable *from inside
  the Docker network* (envoy runs in a container). Ask, don't guess — no
  way to infer this from source code, and a wrong answer here fails
  silently at request time (the route registers fine, then every request
  to it times out or 502s) rather than erroring at onboarding time. Two
  common shapes, both valid — confirm which applies rather than assuming:
  - **A service that's itself a container on this same `docker compose`
    network** — use its compose service name, e.g. `http://my-svc:8000`.
  - **A service running directly on the host** (e.g. `uvicorn`/`npm run
    dev` started outside Docker, like the `demo-user-registration-api`
    worked example) — compose service names don't resolve for this; use
    `http://host.docker.internal:<port>` instead. If unsure which case
    applies, ask the developer directly: "is this running as its own
    container, or on your host machine?"
- **`gateway_type`** — must be `envoy` for the generated payload policy to be
  enforced. The ext_authz→OPA payload-validation wiring only exists on the
  Envoy path today; Kong routes can still be created here, but any
  `payloadPolicyRef` attached to one will be recorded and pushed to OPA
  without anything at the gateway actually evaluating it. Default to `envoy`
  unless the user has a specific reason to use Kong — this is also the
  fleet's `gateway_type` if you end up creating a new one.

### Resolving the fleet (do this before Step 2 — the YAML's hostname depends on it)

`create_route`'s REST/MCP surface has no `fleet_id` or `target_fleet`
parameter anywhere — the *only* thing that associates a route with a fleet,
end to end (mock-psaas's gateway resolution, the console's Fleets/Routes
pages, and the K8s Route CRD's `targetFleet`), is the route's `hostname`
happening to exactly equal a fleet's `subdomain` column. Get this wrong —
typo the hostname, or invent one that matches no fleet — and the route
silently becomes an ungrouped orphan with no error telling you so.

Given the LOB from Inputs, one of three paths:

- **Existing fleet** (the answer to "use one of these" from Inputs) — note
  its `id` and `subdomain` from the `list_fleets` response. **The
  subdomain becomes this route's hostname — don't additionally ask for or
  accept a separately-typed hostname.** This is also why registration in
  Step 5 uses `deploy_fleet`, not `create_route`: `deploy_fleet` resolves
  the hostname from the fleet record itself, so there's no way to typo it.
- **New fleet** — ask for a fleet `name` and a `subdomain` (the actual
  `*.jpm.com` value this will live at). **Do not call `create_fleet` yet** —
  you don't need the fleet to exist to know its subdomain, and creating it
  here would put a fleet in the Console UI before the developer has
  approved anything. Note the planned name/subdomain, use the subdomain as
  the YAML's `hostname`, and hold the `create_fleet` call until Step 5,
  after the publish gate.
- **Standalone route, no fleet** — only if the developer explicitly says
  they don't want this tied to a fleet (mirrors the console's own route
  form, which defaults to "No fleet (standalone route)"). Confirm this is
  intentional rather than assuming it — it's the exception here, not the
  default, precisely because it produces an orphan. If chosen, Step 5 falls
  back to `create_route` with a hostname you ask for directly, same as
  before this section existed.

If the user wants to try this against a concrete, low-stakes example first,
point them at `https://github.com/gavinhamilton1/demo-user-registration-api`
— a small standalone, public FastAPI service (Swagger docs at `/docs` once
running) with exactly the kind of endpoint this skill is built to
demonstrate (see "Worked example" below). Check whether it's already cloned
locally as a sibling of this repo (e.g. `../demo-user-registration-api`)
before cloning fresh over the network — convenient if it's there, but don't
assume it is; this varies per machine.

## Step 1 — Clone and locate route definitions

```bash
git clone --depth 1 <repo> <scratch-dir>/target-repo
```

Then read the source looking for HTTP route declarations. Use `grep`/`Grep`
first to locate candidates fast, then `Read` each hit to understand the
actual handler and its request model — don't rely on regex alone past the
initial search, since decorators can span multiple lines and schemas are
often defined in a separate file from the route.

Framework signatures to look for:

| Framework | Route pattern | Request schema pattern |
|---|---|---|
| FastAPI (Python) | `@app.get/post/put/patch/delete("...")` or `@router.get/post(...)` on an `APIRouter` | A parameter typed as a `pydantic.BaseModel` subclass — find that class's field declarations (`name: type` lines, plus `Field(...)`/validator decorators for extra constraints) |
| Flask (Python) | `@app.route("...", methods=[...])` | Usually manual `request.get_json()` — look for `.get("field")` calls or a marshmallow/pydantic schema used to validate it |
| Express (Node/TS) | `app.get/post/put/delete('...', handler)` or `router.get/post(...)` | Look for a Joi/Zod/express-validator schema referenced in the handler, or a TypeScript interface/type used for `req.body` |
| Django REST Framework | `path("...", views.X)` in `urls.py` | The corresponding `Serializer` subclass's fields |

For each endpoint found, record: HTTP method(s), path (join any router
prefix + route path — e.g. FastAPI's `include_router(router, prefix=...)`),
and — if the method accepts a body — the resolved list of `(field_name,
field_type, format_hint)` from its schema. `format_hint` is your own
classification, not something in the source: look at the field name and any
explicit type (`EmailStr`, a regex validator, a `date`/`datetime` type) to
decide whether it's `email`, `phone`, `date`, or plain `string`/`number`/
`boolean`.

## Step 2 — Generate the Route CRD YAML

One Route per endpoint, following `k8s/crds/route.ingress.jpmc.com.yaml`
exactly. See `examples/route_users_register.yaml` in this skill directory
for a filled-in reference. Key fields:

- `spec.path`, `spec.backendUrl` — from the endpoint plus the `backend_url`
  the user gave you.
- `spec.hostname` — the resolved fleet's `subdomain` (existing or newly
  created), **not** a freeform value, unless the developer explicitly chose
  a standalone route — see "Resolving the fleet" above.
- `spec.targetFleet` — the fleet's `name`, when a fleet was resolved. Omit
  entirely for a deliberately standalone route.
- `spec.methods` — the HTTP method(s) this specific endpoint responds to.
- `spec.authnMechanism` — `"none"` if nothing in the source suggests an auth
  dependency/middleware on this route, `"bearer"` if it does (e.g. a FastAPI
  `Depends(get_current_user)`-style parameter, an Express auth middleware in
  the chain). Don't guess — if you can't tell, ask, defaulting is safer as
  `"none"` for admittedly-public-looking endpoints like `/register` or
  `/health`.
- `spec.payloadPolicyRef` — leave this **out** of the YAML you show first;
  it gets set automatically in Step 4 when the policy is attached, not
  invented ahead of time.
- `spec.notes` — one line saying what was scanned to produce this route,
  so a future reader knows this came from the onboarding agent and not a
  human hand-writing it.

Write each Route YAML into the cloned repo at
`<scratch-dir>/target-repo/ingress/routes/<slug>.yaml` (one file per
endpoint, `<slug>` derived from the path — e.g. `users-register.yaml` for
`POST /users/register`). Writing it inside the target repo's own working
tree — not somewhere ephemeral outside it — is the point: the developer's
existing `git status`/`git diff` on that clone shows these as new files
they can review and, if they want a durable record in their own repo's
history, `git add`/commit themselves. Registering the route against the
live platform (Step 5) is a separate action from this — this step only
produces a file.

Present the full YAML for every discovered endpoint, and say exactly where
you wrote each file, before doing anything else.

## Step 3 — Generate the payload-validation policy

Skip this step for endpoints with no request body (GET, DELETE without a
body). For everything else, generate one Rego file per endpoint using
`examples/route_users_register.rego` in this skill directory as the
template — it's a real, OPA-verified policy (I ran `opa check` and `opa
eval` against five cases: valid payload, SQL injection, XSS, a missing
field + bad email, and a non-object body — all five produce the correct
`allow`/`deny_reason`). Adapt its structure, don't reinvent it:

- **Package name**: `ingress.policy.payload.<policy_id>` where `policy_id`
  matches `^[a-z][a-z0-9_-]{1,63}$` — management-api's `attach_payload_policy`
  rejects anything else, and rejects a `rego_source` whose package
  declaration doesn't match the `policy_id` you pass. A reasonable default:
  slugify the route (`route_users_register` for `POST /users/register`).
- **`required_fields`** — every field the schema marks as required (no
  default value in the Pydantic model / marked `.required()` in Joi / etc).
- **One `<field>_valid` rule per field with a known format**:
  - `email` → `regex.match(`^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$`, ...)`
  - `phone`/`phone_number` → `regex.match(`^\+?[1-9]\d{7,14}$`, ...)` (E.164-ish)
  - `date_of_birth`/`dob`/any `date` typed field → `regex.match(`^\d{4}-\d{2}-\d{2}$`, ...)`
  - anything else → at minimum `is_string`/`is_number`/`is_boolean` per its
    declared type, plus a non-empty check for strings that must be
    non-empty
  - **Always guard with `is_string(...)` (or the appropriate type check)
    before calling `regex.match`** — OPA errors out of the whole evaluation
    on a type mismatch inside `regex.match`, and that error becomes
    fail-open at the gateway (see "Why fail-open matters" below). A type
    guard turns a would-be crash into a clean `deny_reason` instead.
- **No injection-pattern checks here** — see "Two tiers of policy" above.
  The global policy already covers SQLi/XSS/NoSQL markers for every route;
  duplicating that logic in a route-specific policy adds nothing and just
  gives the two policies a chance to drift out of sync over time.
- **`allow`** — true only when the body is an object, every required field
  is present, and every format check passes.
- **`deny_reason`** — a Rego partial set (`deny_reason contains "..." if {...}`),
  one entry per failure so multiple problems in one request all get
  reported at once, not just the first one found.

Write each policy to `<scratch-dir>/target-repo/ingress/policies/<policy_id>.rego`
— same reasoning as the Route YAML in Step 2: it needs to exist as a real
file inside the target repo's working tree so the developer can review and
check it in, independent of whether it ever gets attached to a live route.

**Do not shell out to validate this** — no `opa check`, no `docker run
openpolicyagent/opa`, nothing that pulls images or executes tooling on
whatever machine happens to be running this skill. This step produces
config and a policy file, full stop; it does not touch Docker, does not
assume Docker is even available, and does not side-effect the local
environment. Read the generated Rego back over carefully instead — check
every field access is guarded by the right type check, every `deny_reason`
branch's condition actually matches its message, and the structure mirrors
the template — that's the review this step gets before a human looks at it.

The real compile check happens naturally, later, as part of the platform:
`attach_payload_policy` (Step 5) compiles the Rego in-process on
`management-api` via the OPA Go SDK, and returns a compile error there if
the Rego is invalid. That response is surfaced back to you directly — if it
happens, fix the Rego from the error and call `attach_payload_policy` again.
This is the only validation gate; it's real (an actual OPA compiler
rejecting or accepting real Rego), it costs nothing extra since attaching
the policy was already the next step, and it never requires tooling beyond
the MCP tools already in use for this whole flow.

### Why fail-open matters (read before writing `allow`)

The gateway's enforcement point (`auth-service`'s `checkPayloadOPA`) treats
*any* OPA error, timeout, or "policy not found" response as **allow** — this
is deliberate so a bug in a generated policy can never take down an
unrelated route, and matches the fail-open philosophy already used for the
JWT ext_authz check. It does **not** protect against a policy that
evaluates cleanly to `allow: true` when it shouldn't. Correctness of your
`allow` logic is entirely on you — a policy that silently no-ops (e.g.
`default allow = true` instead of `false`, or a rule that's vacuously true
for `input.body == null`) is worse than no policy, because it looks like
protection to anyone reading the Route CRD's `payloadPolicyRef` field.
Always start from `default allow = false` and build up, exactly like the
template does — never start from `true` and try to subtract bad cases.

## Step 4 — Publish gate (hard stop — nothing is live until the developer says so)

At this point **nothing exists on the platform yet** — no fleet, no routes,
no policy. All that exists is files in the target repo's working tree. That
is deliberate: everything that would show up in the Console UI happens in
Step 5, on the far side of this gate.

Show, for every endpoint:

- The full Route CRD YAML, and the path you wrote it to.
- The full Rego policy (if generated), and the path you wrote it to.
- A one-paragraph plain-English summary: what gets rejected and why, in
  terms a reviewer who doesn't read Rego can sanity-check ("rejects any
  request missing full_name, email, phone, or date_of_birth; rejects
  malformed email/phone/date formats; rejects any field containing
  SQL/script-injection patterns").
- If a **new** fleet is to be created, say so explicitly with the name,
  subdomain, LOB and gateway type you plan to use — it doesn't exist yet
  either, and creating it is part of publishing.

**Then stop and ask, using the `AskUserQuestion` tool — not a question in
prose.** A question in prose is too easy for both sides to skim past; a
tool call forces an actual answer before anything can continue. Offer:

- **Publish to the platform** — create the fleet (if new), register the
  routes, attach the policy. They become visible in the Console UI and
  reachable over the real hostname.
- **Don't publish yet** — keep the generated files, change nothing live.

### What does NOT count as approval

Only an explicit yes to the publish question above is approval. In
particular, **a request that presupposes the routes are already live is not
approval to make them live**:

- "can you test this with a valid payload and a malicious payload"
- "show me it working"
- "does the SQL injection actually get blocked?"
- "what happens if I send a bad email?"

Each of these is a request to *demonstrate* something, phrased as though
publishing had already happened. The reasoning "I can't test it without
registering it, therefore they must want it registered" is exactly the
failure this gate exists to prevent — **this has actually happened**: a
developer asked for a test of a valid and a malicious payload, and the
whole fleet plus three routes were published and appeared in the Console
without anyone ever answering a publish question. The correct response to
any of the above is to ask the publish question *first*, then run the
tests once the answer is yes.

Likewise not approval: silence, a clarifying question, a request to change
the YAML or the Rego, or an answer to some *other* question you asked in
the same turn. If the developer asks for a change, make it, show the diff,
and ask the publish question again.

If they decline, stop cleanly and say what's left behind: the generated
files in the target repo, and nothing on the platform.

## Step 5 — Register (only after approval)

**First, confirm the platform is actually reachable** — call `list_routes`
or `get_platform_status`. If it fails (connection refused, timeout), stop
and tell the developer plainly: the platform isn't running, here's how to
start it —
```bash
cd <ingress-poc repo root> && docker compose up -d
```
(or the kind cluster, if that's the target environment) — then retry once
they confirm it's up. Don't attempt `create_route` against a platform
that's unreachable and report a confusing MCP error as the failure.

**If this is a re-run and `list_routes` already shows routes for this
hostname/path from an earlier attempt, don't patch them with
`update_route` — delete and redeploy via `deploy_fleet` instead.**
`deploy_fleet` is the *only* tool that creates the `fleet_instances` row
linking a route to a fleet (see step 1 below); a pre-existing route from
an earlier `create_route`/`deploy_fleet` call that isn't already linked
into *this* fleet has no way to become linked via `update_route` — it can
only patch fields on the `routes` table. Worse, `update_route` doesn't
even update `fleet_instances.backend` (a separate column the Console's
Fleets page actually reads) — so "fixing" a wrong backend this way leaves
the Console showing the old value forever, even though routing itself
picks up the correction. If you find stale/orphaned routes for this
hostname+path, call `delete_route` on each, then proceed with the normal
`deploy_fleet` flow below as if they never existed.

If a fleet was resolved (the normal case):

**First, if the developer chose a new fleet, create it now** — call
`create_fleet` with the `name`, `subdomain`, `lob` and `gateway_type`
planned back in "Resolving the fleet". The response nests the new fleet's
id at `fleet.id` — that's the `fleet_id` every `deploy_fleet` call below
needs. This is deliberately the first live mutation of the whole flow:
before this call, nothing the developer hasn't approved exists on the
platform.

Then, for each approved endpoint:

1. Call `deploy_fleet` with the fleet's `id`, `context_path` = the
   endpoint's path, `backend_url`, `gateway_type`, and `methods`. This is
   the tool that actually creates the fleet↔route link (a `fleet_instances`
   row with both `fleet_id` and `route_id`), and it resolves the hostname
   from the fleet record itself, so there's nothing to typo. The response
   includes an explicit `route_id` field (distinct from the top-level `id`,
   which is the fleet_instance id) — that's what you pass to
   `attach_payload_policy` next.
2. **`deploy_fleet` has no `authn_mechanism` parameter — it always creates
   the route with `authn_mechanism: "bearer"`, unconditionally.** If Step
   2's YAML determined this endpoint should be `"none"` (a public
   registration endpoint, a health check, etc.), that YAML and the actual
   deployed route now disagree. Fix it immediately after deploying: call
   `update_route` with the returned `route_id` and `authn_mechanism: "none"`.
   Don't silently leave the mismatch — either fix it or tell the developer
   explicitly that this route deployed as bearer-authenticated regardless
   of what the YAML says.
3. If a payload policy was generated for that endpoint, call
   `attach_payload_policy` with the `route_id` from step 1, your
   `policy_id`, and the `rego_source` read from the `.rego` file written in
   Step 3 (the file is the source of truth — if OPA rejects it and you fix
   the Rego, fix it in the file, then retry from the updated file content,
   so what's checked into the repo always matches what's live). If OPA
   rejects it (this tool surfaces OPA's compile error directly), fix the
   Rego and retry — don't fall back to registering the route without
   validation and calling it done.

If the developer explicitly chose a standalone route (no fleet) back in
"Resolving the fleet", use `create_route` instead, exactly as `deploy_fleet`
above but in one call — it does accept `authn_mechanism` directly, no
follow-up `update_route` needed:

1. Call `create_route` with `hostname` (the one you asked for directly,
   since there's no fleet to derive it from), `path`, `backend_url`,
   `authn_mechanism`, `methods`, `gateway_type`, and a `team`.
2. Same `attach_payload_policy` step as above, using the returned `id`.

Report back the route ID(s) and confirm the policy is live (the tool
response includes the route's `payload_policy_ref`, which will now be set).
Tell the developer explicitly:
- **It's now visible in the Console UI** at `http://localhost:3000` (or
  wherever console is exposed) — the Routes page lists the new
  hostname/path, and (if a fleet was resolved) the Fleets page shows it
  grouped under that fleet's LOB section, alongside the fleet's other
  routes — not as an ungrouped standalone entry.
- **It takes a few seconds to actually enforce** — `envoy-control-plane`
  polls for route changes every ~5s, and `auth-service` polls for payload
  policy changes every ~10s. Wait ~10-15s after registering before testing,
  or the very first request or two might not see the policy enforced yet
  (fail-open, so it'll just pass through, not error).

**Then go straight to Step 6 — the run is not finished until the three test
commands have been printed.** Reporting route IDs and a "it's live in the
console" line is not the end of this flow; it's the second-to-last thing
you do.

## Step 6 — Output three copy-pasteable test commands

Once the routes are published, **always end by printing exactly three curl
commands** for the body-carrying endpoint, in this order:

1. **Valid payload** — expect `201` (or `200`), body comes back from the
   backend.
2. **Malicious injection payload** — expect `403`, caught by the *global*
   policy, `reason` is the generic injection message.
3. **Invalid field format** — expect `403`, caught by the *route-specific*
   policy this skill generated, `reason` names the offending field.

Point out which of the two policy tiers catches #2 versus #3 — that
contrast is the whole point of showing three commands rather than two.

**Running the commands yourself is not a substitute for printing them.**
It's fine — often useful — to execute them and show the developer the
actual status codes and `deny_reason` bodies you got back. But a results
table is something they can only read; three pasteable lines are something
they can re-run themselves, hand to a colleague, or drop into a demo
script. If you only show results, they have to reconstruct the commands
from your prose to do anything with them. Print the commands **and**, if
you ran them, the results — in that order, commands last, so the final
thing on screen is the thing they'll copy.

Done means: the three commands are in the final message, each on one line,
with the real hostname and path substituted in.

### Formatting rules for the emitted commands — these matter

- **One line per command. No line breaks inside a command, no `\`
  continuation markers, no leading `>` or `$` prompt characters.** The
  developer copies one line, pastes it, and it runs. A command split
  across lines with backslashes breaks the moment it's pasted into
  anything that reflows or strips them (chat, a ticket, a doc, some
  terminals) — and a half-pasted curl that silently hangs on a
  continuation prompt is a worse demo than no demo.
- **Never put a literal `'` inside the payload.** The `-d` argument is
  single-quoted, so an apostrophe inside it terminates the string — the
  classic `Robert'); DROP TABLE users;--` payload *cannot* be written on
  one line without `'"'"'` escaping noise that defeats the purpose. Use a
  quote-free injection payload instead; `Robert; DROP TABLE users--` is
  caught by the global policy exactly the same way (verified against a
  live route), and so are `1 UNION SELECT * FROM users` and
  `<script>alert(1)</script>`. If you want a payload with double quotes,
  JSON-escape them (`admin\" OR 1=1--`) — that survives single-quoting
  fine.
- Substitute the real hostname and path — never leave `<hostname>` or
  `<path>` placeholders in commands you hand over.

### The three commands (worked example — substitute your own hostname/path)

```bash
curl -i -X POST https://demo-user-api.jpm.com/api/v1/users/register -H "Content-Type: application/json" -d '{"full_name":"Ada Lovelace","email":"ada@example.com","phone":"+14155552671","date_of_birth":"1990-01-01"}'
```


### Which URL form to emit

Testing directly against `gateway-envoy` (`localhost:8000`) skips the whole
simulated CDN front door (GTM/Cloudflare LB, edge WAF, PSaaS) — fine for
narrow debugging, but not what "test it using the jpm.com domain" means.
The actual front door in this stack is `mock-multi-cdn-traffic-manager` on
**port 8010 (HTTP) / 443 (HTTPS)**, which then randomly picks the Akamai or
Cloudflare simulated path before reaching the same gateway. Run the valid
command a few times and the `X-Multi-Cdn-Provider-Selected` response header
alternates — the result is identical either way, both paths converge on the
same platform.

**Preferred: the real hostname over HTTPS, as above — no port, no `Host`
header.** This repo's `dns` container (CoreDNS) plus its host DNS setup
makes `*.jpm.com` resolve to `127.0.0.1` directly. Confirm before emitting
this form with `dscacheutil -q host -a name <hostname>` (should show
`127.0.0.1`). This is the truest "real world" demo — the same URL a browser
would actually hit. It needs no `-k`, provided
`./scripts/setup-local-network.sh` has been run to trust `certs/jpm.com.crt`
(check with a single request; add `-k` to all three commands only if the
cert genuinely isn't trusted, and say why you added it).

**Fallback: explicit `Host` header against port 8010**, if DNS isn't set up
on this machine — works everywhere, no setup needed, still one line each:

```bash
curl -i -X POST http://localhost:8010/api/v1/users/register -H "Host: demo-user-api.jpm.com" -H "Content-Type: application/json" -d '{"full_name":"Ada Lovelace","email":"ada@example.com","phone":"+14155552671","date_of_birth":"1990-01-01"}'
```

Without editing local DNS, adding `--resolve <hostname>:443:127.0.0.1` to
the preferred form gets the same real-hostname-over-HTTPS effect for one
command, with no resolver setup at all.

**`/health` is a special case — don't use it for this demo.** Both port
8010 and port 443 on `mock-multi-cdn-traffic-manager` hardcode their own
`/health` route (the traffic manager's own liveness check) that intercepts
*any* request to that path regardless of `Host`/hostname — it never
reaches your fleet's `/health` route at all, even if one is registered. If
you need to demo a registered `/health` route specifically, test it
against `gateway-envoy` directly (`http://localhost:8000/health` with the
`Host` header) — that layer has no such reservation. Prefer a
body-carrying endpoint (like `/api/v1/users/register` here) for the main
demo regardless, since that's what actually exercises the payload policy.

Command #2 above is caught by the **global** policy (every route gets that
check, not just this one); command #3 is caught by the route-specific
policy this skill generated, and its `deny_reason` names the offending
field. That's why both are in the set — showing only an injection block
proves nothing about the policy this skill just wrote. A request missing a
required field entirely is another good route-policy demo: the
`deny_reason` set returns *every* failure at once, not just the first.

If you want to isolate "is this the CDN simulation or the gateway policy
that's doing X" while debugging, hitting `http://localhost:8000<path>`
with the same `Host` header talks to `gateway-envoy` directly, skipping
the CDN layer but still enforcing the same route/payload policy — useful
for narrowing down a problem, not the primary way to demo this to someone.

### If #1 returns 503 while #2 and #3 correctly return 403

That combination means the **backend cluster**, not the policy. A 503 here is
the request having *passed* both policy tiers and then failing to reach the
backend, so the natural instinct — that the generated Rego is wrong — is
exactly backwards. Check the address family Envoy resolved for the backend:

```bash
curl -s localhost:9901/clusters | grep "<route-slug>::.*health_flags"
```

An IPv6 endpoint (`[fdc4:...]:<port>`) with `/failed_active_hc` means Envoy
picked an AAAA record the gateway container can't route to — the failure mode
`host.docker.internal` backends hit, since compose service names resolve A
records only. `cmd/envoy-control-plane/main.go` pins `dns_lookup_family:
V4_ONLY` on its generated clusters to prevent this; if you see it anyway, that
setting has been dropped or the control plane is running a stale image. A
healthy endpoint shows an IPv4 address and `health_flags::healthy`.

Two other things worth ruling out before touching the policy: the backend must
actually be running (a host-run `uvicorn` dies with its terminal), and the
fleet must still exist — deleting a fleet from the Console takes all its routes
and their attached policies with it, so an onboarding can evaporate minutes
after it succeeded. `get_audit_log` shows `DELETE_FLEET` entries if that's what
happened.

## Worked example — demo-user-registration-api

`https://github.com/gavinhamilton1/demo-user-registration-api` (public; may
already be cloned locally as a sibling of this repo — check before cloning
fresh, but don't assume a specific path, it varies per machine)
is a small, purpose-built FastAPI service for exercising this exact flow —
use it as a first run before pointing this skill at anything more complex or
external. It has real Swagger docs (run `.venv/bin/uvicorn app.main:app
--port 8123` from the repo root, then open `http://127.0.0.1:8123/docs`) if
you want to look at the schema visually rather than just reading source.

- `app/routes/users.py` — `POST /api/v1/users/register` and
  `GET /api/v1/users/{user_id}`, mounted under prefix `/api/v1` in
  `app/main.py`.
- `app/models.py` — `UserRegistration` (`full_name: str`, `email: EmailStr`,
  `phone: str` with a field validator for `^\+?[1-9]\d{7,14}$`,
  `date_of_birth: date`).

Scanning it end-to-end should produce exactly the YAML and Rego already
checked into `examples/route_users_register.yaml` and
`examples/route_users_register.rego` in this skill directory — if your

check your scan before presenting it for review, not necessarily a sign the
example is right and you're wrong, but worth reconciling the difference
explicitly.

This service has no existing fleet — running through "Resolving the fleet"

exercise. The example YAML's `hostname`/`targetFleet` values assume this.
