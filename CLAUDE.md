# ingress-poc — notes for Claude Code

A local, fully-Dockerized simulation of an enterprise ingress platform: CDN/WAF →
regional perimeter → Envoy/Kong gateways → two-tier OPA payload policy → backend.
Includes a management console, an agentic "onboard a repo" skill, and animated
diagrams of both flows. This file exists so a fresh Claude Code session on a new
machine doesn't have to rediscover the non-obvious parts below.

## Get it running

```bash
git clone <repo-url> ingress-poc && cd ingress-poc
docker compose up --build          # first run takes a few minutes
```

That alone gives you everything the README's "Option A" describes — console at
`http://localhost:3000`, and hostname-based testing via
`curl -H "Host: <hostname>" http://localhost:8010/...`. **Do not use the kind/k8s
path in the rest of the README ("Option B" / Part 1-2) unless the user explicitly
asks for it** — this whole project has been driven via plain `docker compose` all
along, not kind clusters or Argo CD.

### One-time host setup (for browsing real hostnames, not just `Host:` header curl)

Two things this repo needs that `docker compose` does **not** set up for you,
because they're changes to the host Mac, not the containers:

```bash
./scripts/setup-local-network.sh
```

This creates `/etc/resolver/jpm.com` (routes `*.jpm.com` DNS to the `dns`
container on port 5553) and trusts `certs/jpm.com.crt` in the System keychain
(the cert itself **is** checked into git, despite `certs/*.key` being in
`.gitignore` — `jpm.com.key` was added before that rule existed and stays
tracked). Without this step, `https://demo-user-api.jpm.com` or
`https://jpm.com:3443` won't resolve/won't be trusted in a real browser — you'd
be stuck with the `Host:` header curl trick. Script is idempotent; safe to
re-run. macOS only.

**Console login**: pick any demo user (Admin/Trader/Read-Only), password `demo1234`.

**Also serves HTTPS on port 3443** (`https://jpm.com:3443`), not just plain
`:3000` — added because `crypto.subtle` (used for PKCE login) is unavailable in
a non-HTTPS, non-localhost browser context.

## Critical environment gotcha

**Never let this repo (or its sibling `demo-user-registration-api`) live inside
a cloud-synced folder** (OneDrive, iCloud Drive, Dropbox, etc.). OneDrive in
particular uses a macOS File Provider extension that doesn't support `mmap`
properly, and git relies on `mmap` for its index — every git command fails with
`fatal: mmap failed: Operation timed out`. Keep both repos under a plain local
path like `~/dev/...`. If you ever see that exact error, this is the cause —
relocate the repo, don't try to fix git itself.

## Platform architecture — the tier model

This is the model the console's diagrams (`/traffic-flow`, `/protection-architecture`)
and the onboarding skill all agree on. Get this right before touching routing code:

- **Public internet** (untiered): Client → Global Traffic Management (Akamai
  GTM / Cloudflare LB, mocked) → CDN Edge (Akamai/Cloudflare edge + WAF, mocked).
- **Tier 1 — Perimeter**: `mock-psaas`, standing in for **either** PSaaS+
  (on-prem/private datacenters) **or** AWS WAF (AWS-hosted workloads) — two
  parallel paths in the real architecture, one mock service here.
- **Tier 2 — Gateway (the trust boundary)**: the actual gateway (Envoy/Kong)
  **and both OPA payload-policy checks** all live in this one tier. Nothing
  reaches Tier 3 without clearing the gateway, the global policy, and (if
  attached) the route-specific policy.
- **Tier 3 — Trusted internal**: the onboarded backend service itself.

**Two-tier OPA policy, both enforced by `auth-service` inside Tier 2:**
1. **Global policy** (`ingress.policy.payload.global`) — generic SQLi/XSS/NoSQL
   injection-pattern checks, applied to *every* route with a body, updated via
   `update_global_policy` (one change protects everything at once).
2. **Route policy** (per-route package, e.g. `route_users_register`) — schema
   checks only (required fields, email/phone/date formats) generated by the
   onboarding skill from the target repo's own model. Deliberately does **not**
   duplicate injection checks — that's the global policy's job.

**Routing quirk worth knowing**: the shared `gateway-envoy` container only
serves routes with no `route_node_assignments` row (an "unassigned" query in
management-api) — fleets with their own dedicated envoy nodes get pushed there
*too* via `deploy_fleet`, which never populates that table. In practice this
means routes registered through `deploy_fleet` (what the skill and the
console's own UI use) end up served by the shared gateway for `/api/*` paths
regardless of the fleet's dedicated nodes — this is intentional per
`mock-psaas`'s own perimeter simulation ("route /api/* to Kong-designated
routes, else to Envoy"), not a bug.

**A `host.docker.internal` backend needs `dns_lookup_family: V4_ONLY`**: Envoy
defaults `STRICT_DNS` clusters to `AUTO`, which prefers an AAAA record when one
exists. Plain compose service names only ever resolve A records, so this never
mattered until the first host-run backend — `host.docker.internal` resolves to
an IPv6 ULA on Docker Desktop that the gateway container has no route to, so
Envoy picks that sole endpoint and every request dies in active health checks.
The symptom is maximally misleading: the route is correct, both payload
policies *pass*, and the 503 arrives afterward, so suspicion lands on the
policy. `cmd/envoy-control-plane/main.go` now pins `V4_ONLY` on all four
generated clusters — don't drop it. To confirm the address family in a live
gateway: `curl -s localhost:9901/clusters | grep <cluster>::.*health_flags`.

## The onboard-repo skill

Lives at `.claude/skills/onboard-repo/`. Scans a target repo for HTTP routes +
request schemas, generates a Route CRD YAML + an OPA Rego policy, gets a human
review/approval, then registers both via the `cib-ingress` MCP tools
(`create_fleet`/`deploy_fleet`/`attach_payload_policy`/etc., backed by
`management-api` on `:8003`).

Known pitfalls already documented in the skill itself — read it before
"fixing" these again:
- `deploy_fleet` always creates the route as `authn_mechanism: "bearer"` —
  follow up with `update_route` if the endpoint should be public.
- `update_route` only patches the `routes` table, **not**
  `fleet_instances.backend` — the Fleets page reads the latter. If you're
  correcting a wrong backend URL on an already-registered route, delete and
  redeploy via `deploy_fleet` rather than `update_route`.
- A path with a `{param}` segment (e.g. `/api/v1/users/{user_id}`) needs
  Envoy's `safe_regex` matching (already fixed in
  `cmd/envoy-control-plane/main.go`'s `pathToRouteMatch`) and the same
  template-aware matching in `cmd/mock-psaas/main.go`'s
  `lookupRouteGatewayType` — both already handle this; don't reintroduce a
  literal-prefix match.

**Worked example / demo target**: `demo-user-registration-api`
(`https://github.com/gavinhamilton1/demo-user-registration-api`). Clone it as
a sibling of this repo if it isn't already there — **not** inside OneDrive
or any other cloud-synced folder (see above). Run it with
`.venv/bin/uvicorn app.main:app --port 8123` from its repo root; register its
routes with `backend_url: http://host.docker.internal:8123` since it runs on
the host, not in a container.

## Console pages worth knowing about

Beyond the standard Fleets/Routes/Sessions/etc. pages, three were built
specifically to demo this platform on video:

- `/onboarding-flow` — step-by-step animated walkthrough of the onboard-repo
  skill (`console/src/pages/OnboardingFlow.jsx`).
- `/traffic-flow` — animated request simulator with three buttons (valid /
  malicious-SQLi / invalid-format) showing live per-stage checks, the tier
  bands, and both TLS boundaries (`console/src/pages/TrafficFlow.jsx`).
- `/protection-architecture` — static defense-in-depth reference diagram, one
  block per hop (`console/src/pages/ProtectionArchitecture.jsx`).

If asked to extend these, keep the color language consistent between
`TrafficFlow.jsx` and `ProtectionArchitecture.jsx` (gray=public,
orange=Tier 1, blue=Tier 2/gateway, cyan=global policy, green=route
policy/Tier 3) — they're meant to read as one system.

## Local console dev iteration

`console/vite.config.js` has a dev-only proxy for `/_proxy/auth` and
`/_proxy/management` to the host-exposed container ports, so
`npm run dev` (or the `console-dev` launch.json config, port 5174) works
without nginx in front. Note: `console/node_modules/` **is** checked into
this repo (unusual, but intentional here) — only `console/node_modules/.vite/`
is gitignored.

## `.claude/` tracking convention

If you add or edit a skill (or `launch.json`), **commit it** —
`.claude/skills/` and `.claude/launch.json` are meant to travel with the
repo; that's the only way a skill exists on someone else's clone.
**Never commit `.claude/settings.local.json`** (it's gitignored on
purpose) — it's per-user and can carry things like a `disabledMcpjsonServers`
entry that would silently break a skill's MCP dependency for anyone who
inherited it. This distinction wasn't obvious and cost a full round-trip to
discover once already — the skill existed locally for an entire session
before anyone noticed it had never actually been pushed.
